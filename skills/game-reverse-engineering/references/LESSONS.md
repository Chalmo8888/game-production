# 三个实际项目的经验（证据与推断分开）

来源：2026-10-19 对三个本地项目的只读审计，内容包括文档、源码规模和 Git 历史。下文路径都是相对各项目目录的路径。
- **【证据】**：有文件、数据或提交记录直接支持。
- **【推断】**：根据证据得出的判断，作为建议使用，尚待在新项目中验证。

这些经验已经转化为本 Skill 的规则和工具检查，对应关系见每节末尾。

## 《二战前线》：研究不断深入，成熟 Base 迟迟没有建成
项目由四个工程组成：原创试作、SWF 研究、原作机制重建、正式发行工程。

**发生了什么**
- 【证据】机制重建工程的 74 次提交中，73 次是复刻原作细节（例如 "Restore Boss47 orb hit shape"）；唯一一次 Base 相关提交（"Add atlas animation presentation base"）是最后一次。仅 Boss47 就有约 10 次提交。
- 【证据】正式发行工程从研究中只继承了 7 个常量（`src/core/baseline.ts`），并锁定在旧版本；它在研究还持续进行时就停止了更新，停了约 46 小时。
- 【证据】项目自己的 `CAPABILITY_PARITY_MATRIX.md` 中，Logic / Presentation / Creator Ready 三道门禁全部未通过；音频总线、动画状态机、资产批量导入、主题替换都标为“未实现（P0）”，原话是“研究/QA文档丰富，制作侧说明不足”。
- 【证据】`TODO.md` 中 P0 的第 0–9 项都是原作保真，Base 排在第 10–12 项。
- 【证据】`FULL_CODE_AUDIT.md` 统计了 1,359 个脚本，但“尚未完成语义分类的脚本 1,359”。动态运行（Ruffle）停在加载条，所以大部分结论只能是 STATIC_ONLY，研究没有自然的终点。
- 【证据】`simulation.ts` 约 210 KB，Boss 逻辑集中在一个单体文件中；矩阵自评为“Boss逻辑仍集中在simulation”。

**做得好的部分**
- 【证据】分层提取：SWF 容器统计 → 函数头索引 → 源码视图与 P-code 双视图交叉校验 → 只含位置、哈希和调用边的证据索引（不含源码正文）。
- 【证据】五态证据词汇表（`EVIDENCE_STATUS.md`：VERIFIED / STATIC_ONLY / INFERRED / PROXY / UNKNOWN），以及代理债务表（`PROXY_DEBT.md`）。
- 【证据】证据接入 CI：哈希重算、生成表防漂移、发行包闭包校验。
- 【证据】只认正常输入通关：固定种子的输入控制器，禁止降伤、扩平台或 QA 清场。
- 【证据】研究原件（SWF、反编译输出、资源）被 `.gitignore` 排除，并有诚实声明：“不是严格洁净室实现”。

**转化为本 Skill 的规则**
- 研究任务必须指向矩阵条目（`task start --kind research --item`）；连续研究而矩阵没有进展会触发 RESEARCH_SPIN。
- E0 就建立 Base 骨架和 core_paths；等级按能力覆盖度判定，不按原作保真度。
- 动态运行能力是 E0 的必答问题；做不到时，静态条目必须写 dynamic_gap，并接受较低的保真目标【推断】。
- 逻辑重建要求组件化、数据驱动，禁止单体模拟文件（LOGIC_REBUILD）。
- 事实可信度（original.evidence_level）和 Base 能力状态（status）是两列，不能混在一起。

## 《植物大战僵尸》：只迁移了玩法逻辑，遗漏了成熟的表现体系
项目由三部分组成：研究基座（反编译 C++ 移植编译为 WASM）、洁净室思路的商业重写 Base（TS + Canvas），以及从商业 Base 整仓克隆出的 Game 01。

**发生了什么**
- 【证据】许可矩阵把原版动画/粒子/拖尾/Foley 库列为不可迁移，替换方式写的是“新动画/粒子系统”，但可迁移清单里没有任何表现能力。交给重写方的 `BEHAVIOR_SPEC.md` 中，表现只占 §9 的三条。
- 【证据】`PARITY.md` 只对照玩法机制；Game 01 的整个动画运行时只有约 70 行，只能按行列取帧。
- 【证据】表现逆向审计（`PRESENTATION_REVERSE_AUDIT.md`）晚于 Game 01 的发行候选版本，原话：“第一轮只做到'资源能被引擎接受'，没有研究表现能力本身”。它列出了原版具备、移植版没有的能力：轨道插值部件动画与混合过渡、挂接树与挂点矩阵、复合排序键、独立阴影层、曲线参数粒子与预算、加法混合与受击闪白、运行时图集、九宫格 UI、位图字体、拟音的变体与去抖、对象池。
- 【证据】商业 Base 后来补出了表现运行时 v2（约 +2.7k 行），但 `visuals.json` 中 `"units": {}`，没有任何真实资产在用；它引用的 `ANIMATION_RUNTIME_SPEC.md` 并不存在。【推断】Game 01 停在旧 Base 上，v2 从未进入已发布的游戏。
- 【证据】QA 记录“棋盘像高亮调试网格”“命中只做叠色”；软件渲染帧时 31.37ms，门槛 32ms。

**做得好的部分**
- 【证据】资源管线：从源码提取契约 → 占位生成 → 导入 → 校验 → 分层覆盖，并把“影响玩法的动画数据”（如移动轨道、时序钩子）写进校验器。
- 【证据】上游代码按原样提交隔离，修改记录单独保存；素材按 A/B/C/D 分类，刻意模仿原版造型的素材不迁移。
- 【证据】“代表关卡放行后才量产”。

**转化为本 Skill 的规则**
- E3 必须为 P1–P8 建立条目，PRESENTATION_READY 是独立等级，表现能力域不能整体 N/A。
- 表现条目 VERIFIED 必须有运行时录制或测量证据（意味着至少有一个真实资产在运行），单元测试不够。
- 洁净室或重写规格必须同时覆盖机制与表现（PRESENTATION_2D 给出最少清单）。
- 影响玩法的隐式契约要进校验器；文档中引用的规格文件必须存在【推断：建议作为 CI 检查】。
- Base 新版本要有依赖游戏的改绑与回归路径（沿用 v4 的版本绑定）。
- 离线烘焙等降级方案必须写进 differences，不能当作等价实现。

## 《勇者之路》：值得推广的工程实践，以及需要防止的失败模式
项目是 Phaser 3 + TS 的 H5 动作游戏，代码中名为《晨曦之刃》。

**值得推广（有证据）**
- 【证据】数据驱动关卡：`src/data/stages.ts` 的段落格式 `Seg {w, gap, plats, spawns, arena, …}`，由 `Level.layout()` 统一生成；新机制只需加一个字段。设计约束写成单元测试（如间距上限、禁止坑内浮台）。
- 【证据】拆件骨骼动画：`heroRig.ts` 有 14 根骨骼（pivot、attach、scale、flip、back），姿势是一组角度加混合时长；运行时做正向运动学、插值，取两脚中较低者贴地。用映射层把旧帧名映射为姿势后，`Player` 状态机一行没改（提交 `26b7c1e`）。
- 【证据】切件工具在块数不对时直接失败（`build_rig.py`：`SystemExit`）。
- 【证据】自动 Sprite 管线：生成任务 JSON → 去背（边框中位色与连通区域）→ 按期望数量切帧（失败时降阈值，再用分水岭分割）→ 排序 → 打图集 → 联系表预览 → 统一缩放。
- 【证据】长期接续：AGENTS（硬约束与事故规则）、PROGRESS（只记录已验证内容）、TODO、QUALITY_GAP（维度/状态/证据/差距）。主会话被压缩 5 次、换过一次模型，仍能续上。

**需要防止（有证据）**
- 【证据】静态逆向浅尝辄止：`research/05_confidence.md` 写明“需要实机游玩，本研究没有运行 Flash”，手感参数一项都没拿到，后期的手感问题全靠真人发现。
- 【证据】过早宣布完成：开工约 3 小时就宣布完成；洞穴软锁经过约 6 轮修复后仍被用户推翻；e2e 的 Boss 用例用 `onHit(hp+1)` 直接秒杀。
- 【证据】长期低价值打磨：239 个提交中，`juice:` 44 个、`polish:` 41 个，集中在约 13 小时内，单小时最多 34 个；同期手感、Boss 帧、画风一致性等主要短板没有推进。
- 【证据】测量只是报告，不是门禁：落地和地形统计只打印结果，没有阈值断言；点击偏移、血条遮挡都是真人发现的。
- 【证据】重要记录被覆盖：`qa/playthrough.json` 被覆盖后，“CAMPAIGN 15/15”已无法复核；PROGRESS 中的测试数量过期（写 31 项，实际 54 项）。
- 【证据】一次 Grep 挂起约 3.1 小时，Agent 没有察觉。

**转化为本 Skill 的规则**
- 原版 UNKNOWN 的行为不得进入实现（除非标为 IMPROVE 独立设计）；手感类参数需要动态测量或明确写出缺口。
- 表现验证要求测量类证据；能测的视觉项要写成带阈值的断言（PRESENTATION_2D 的测量清单）。
- 管线每一步都有期望数量门禁，不符合就失败，而不是只打印 WARNING（ASSET_ANIMATION_PIPELINE）。
- 验收走玩家路径：禁止秒杀、跳关、改血类测试冒充通关（LOGIC_REBUILD）。
- 证据按时间戳另存、历史只追加（`gre.py evidence`、HISTORY.jsonl）；状态数字以工具输出为准，不手写。
- 任务带超时，超时即提示 STALLED；目标未达成时连续打磨会触发 POLISH_SPIN（阈值默认 5 个任务【推断】）。
- 等级只能由证据支持，不能由 Agent 宣布。

## 1.1.0 新增的规则与它们的来源
- **游戏特有能力发现**：《植物大战僵尸》的表现能力和《二战前线》的多部件 Boss，在通用清单之外都有大量原作特有的系统；只按模板检查会漏掉这些系统【推断：由这两个案例归纳】。
- **能力来源分类**：《二战前线》曾把“符号名存在”写成“行为已验证”；《勇者之路》的手感参数完全没有动态证据【证据】。所以未知行为只能作为 EXTENSION 独立设计，不能写成 PARITY。
- **Creator 生产能力测试必须包含玩法改动和完整循环**：《植物大战僵尸》的表现运行时 v2 只有测试，没有真实资产（`units: {}`）；《二战前线》的 Creator Ready 只停留在“主题替换”的设想【证据】。只换素材证明不了生产能力【推断】。
- **价值驱动排序、研究预算、阻止连续打磨**：《二战前线》中原作保真占满了 P0，Base 被排在第 10–12 位；《勇者之路》在 13 小时内有 85 个 juice/polish 提交，主要短板没有推进【证据】。预算 3 次、阈值 5 个任务这两个数值是【推断】。
- **代码改动后旧 QA 失效**：《勇者之路》的“CAMPAIGN 15/15”在代码继续改动后已无法复核【证据】。
- **安全恢复超时任务**：《勇者之路》中一次 Grep 挂起约 3.1 小时没有被察觉【证据】。

## 1.2.0 新增的 Presentation Reconstruction 与它的来源
- 《植物大战僵尸》的表现逆向审计列出了原作的复合排序键（`分层基数 + 行号×10000 + 偏移`）、挂接树与挂点矩阵、独立阴影层、加法混合、九宫格 UI、运行时图集，以及“影响玩法的动画数据”（如移动轨道）【证据】。这些正是 PR01–PR10 调查项的来源：只迁移资源和玩法，就会丢掉这些画面组合机制。
- 同一项目中，表现运行时 v2 只有单元测试，没有真实场景（`units: {}`）；Game 01 的场景层顺序和 HUD 安全区写在游戏仓库里，不在 Base 中【证据】。因此门禁要求在 Base 中搭建可配置的代表性场景（PX01–PX08），并通过多份场景配置证明可以重新组装。
- 《勇者之路》的脚点问题被真人推翻，测量只停留在报告层面【证据】。所以 PX02、PX06、PX07 要求测量证据，并在锚点或场景文件变化后自动过期。
- 《二战前线》的 Presentation Ready 停在 Canvas 调试图形，动画状态机与音频事件总线都未实现【证据】。PX04、PX05 要求动画播放与事件时序有真实证据。

## 尚未验证的假设
- 研究与建设任务的合适比例（例如每 3 个研究任务至少要有 1 个建设或验证任务）【推断】。
- 不同类型游戏的阈值（脚点漂移、帧时预算等）应由项目自己测定；文中出现的 2px、32ms 只是那些项目当时使用的值。
- 两套 Creator 测试配置能否代表真实新游戏的需求，还需要在第一款基于 Base 的游戏中复核。
