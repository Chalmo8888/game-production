# 按游戏类型加检查，不按游戏类型重建整套流程

读取当前游戏对应的段落，不要求所有游戏具备所有机制。2D/3D、单机/联机来自该游戏的 GAME_DESIGN 与 GAME.json scope，不能默认强加。同一个 Base 上的不同游戏可以属于不同的子类型，按各自类型检查。

## 塔防 / 分行防御
部署合法性、资源收支、卡冷却、阻挡与绕行、弹道与目标选择、地形条件、波次时序、护甲/状态效果、清场与失败条件、应急机制。平衡覆盖所有计划交付的单位，避免自动玩家永远只用一种阵容。生成式/无尽模式测压力和软锁，不宣称“全通无尽”。

## 横版射击 / 动作平台
固定步进与输入时序、跳跃轨迹、上下身/武器挂点、攻击帧、真实二维关卡、相机与边界、封锁与出口、敌人状态及死亡回调、Boss 阶段和碰撞。不能水平化纵向地图、用全通用 AI 冒充完整行为、只靠 Boss 减血结算证明还原。

## 横版 ARPG / RPG
动作取消与命中、技能与耗费、装备实际效果、物品掉落、地图通行、任务状态、成长曲线、NPC 交互、存档迁移。背包 UI 存在不代表装备逻辑完成。剧情必须在游戏中发生，不能只在文档里。

## 肉鸽
随机种子、构筑分布、升级/掉落配方、效果组合顺序、击中去重、敌人/弹体数量上限、Boss 时序、正常运行长度。比较多种构筑，不只自动选择最强路线。已有 Base 核心稳定边界不得随意突破。

## FPS / 3D
相机、碰撞体、世界单位、模型米制/比例、武器视角、射线/弹丸、遮挡、AI 导航、交互范围、GLB 资产层级、动画绑定与预算。不能只通过模型加载成功判定实机可见正确。无需美术时用明确标记的调试资源。

## 基于可复用 Base 的游戏
只通过游戏目录里的配置、内容和资产实现本游戏，不修改 Base 核心。需要新的通用能力时按 [HANDOFF_CONTRACT](HANDOFF_CONTRACT.md) 回报上游，由 game-reverse-engineering 升级 Base 版本，游戏改绑后回归。内部路径、ID、注册表等由 Agent 处理，不让普通创作者先学技术术语。
