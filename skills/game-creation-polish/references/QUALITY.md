# 游戏质量门禁、证据与反自我放行

## 基本语义
`games/<id>/.production/GATES.json` 是本游戏门禁状态的唯一记录。状态有五种：PASS 必须有实际证据；FAIL 表示已观察到缺陷；UNVERIFIED 表示尚未验证；BLOCKED 表示缺少工具、权限或外部条件；NOT_APPLICABLE 只用于目标范围确实不需要的情况，并写明依据。

不能用综合分数或测试通过数量掩盖单项的重大失败。验收标准根据用户目标制定，落实到具体的输入、结果和阈值后锁定，事后不得降低。确实需要修正错误的标准时，保存理由、旧标准、新标准和依据，“更容易通过”不能作为理由。

## Base 不在本 Skill 验收
Base 的研究、表现还原、创作者工具包、首次使用和独立复用由 game-reverse-engineering 验收，结果通过创作交接（[HANDOFF_CONTRACT](HANDOFF_CONTRACT.md)）传入。本 Skill 不重新判定 Base，也不能因为游戏做得好就把 Base 视为合格。交接低于 CREATOR_CANDIDATE、文件被改动或缺失时，游戏不能达到 GAME_READY。

## 游戏门禁
| ID | 检查对象 | 最少应有的证据 |
|---|---|---|
| D01 | 游戏策划 | 填写完整的 GAME_DESIGN（工具检查 17 节和模板标记）、任务已进入 BACKLOG |
| D02 | 美术策划 | 三份美术文档 + 至少一个 verified 的代表资产 |
| Q01 | 逻辑与机制 | 规则、对 Base 的配置扩展、游戏专有逻辑的测试 |
| Q02 | 内容完整与差异 | 范围内关卡/单位/武器的清单与实际使用覆盖，各自的作用差异 |
| Q03 | 真实操作通关、地图碰撞、平衡 | 从正式入口通关、失败、重开；多策略、多种子；无隐形墙或软锁 |
| Q04 | 美术、动画、视觉一致性 | 连续动作序列、脚点挂点、风格一致、无静默占位；与 Base 场景几何契约一致 |
| Q05 | UI/UX 与音频 | 多窗口截图、遮挡检查、实际播放与音量总线 |
| Q06 | 存档与状态 | 刷新、恢复、损坏回退、旧版本存档、与其他游戏的存档隔离 |
| Q07 | 性能与分辨率 | 目标设备与多分辨率下的帧时间、内存、负载场景 |
| Q08 | 资源与内容来源许可 | RIGHTS_LEDGER + ASSETS.json 中每项资产的来源和许可 |

## 发行门禁（同一个 GATES.json）
| ID | 检查对象 | 最少应有的证据 |
|---|---|---|
| R01 | 构建与包完整性 | 干净构建、产物哈希、资源完整，不含研究原件、密钥或私有路径 |
| R02 | 目标平台适配 | 真实平台规范的来源与版本和实测结果；仅本地候选时标 N/A 并写依据 |
| R03 | 权利审查就绪 | 交接中的 Base 权利状态（RE01/RE03）+ 本游戏 Q08 汇总，待确认事项清单 |
| R04 | 公开发布批准 | 用户或权利人的批准记录，reviewer.independence = external_approval |

**Base CREATOR_READY ≠ GAME_READY ≠ PUBLICATION_APPROVED。** Base 合格不代表基于它的游戏合格；Game 01 通过不代表 Game 02 可以发布；技术候选就绪不代表权利审查通过；权利审查材料齐全也不代表获准发布。

## 就绪度
| 级别 | 需要（PASS，或带依据的 NOT_APPLICABLE） | 额外条件 |
|---|---|---|
| FEATURE_COMPLETE | D01、Q01、Q02 | Q 门禁的 `base_version` = 游戏绑定的版本 |
| GAME_READY | + D02、Q03–Q08 | 绑定版本的最新创作交接完整且 ≥ CREATOR_CANDIDATE |
| RELEASE_CANDIDATE | + R01、R02 | 已记录产物路径与 SHA-256，并且一致 |
| PUBLICATION_APPROVED | + R03、R04 | Q08、R03、R04 必须 PASS；R04 为 external_approval；交接中 RE01 = PASS，RE03 = PASS 或 NOT_APPLICABLE |

阶段 DONE 也会被检查：G1 需要 D01，G2 需要 D02，G5 需要 GAME_READY，G6 需要 RELEASE_CANDIDATE，G7 需要 G6 完成并写好 retrospective.summary。

## 证据绑定
每个 PASS 至少记录：被测的代码/资产快照（subject_revision）、验证时绑定的 Base 版本（base_version）、命令或操作路径、环境、观察结果、证据的相对路径和 SHA-256、检查者及其独立性。相关输入变化后，重跑受影响的测试。改绑 Base 后，旧版本的 PASS 不再计入新版本的就绪度。

证据文件存在只能证明文件存在；摘要与哈希一致只能证明引用一致，不能证明游戏好玩或结论真实。辅助校验器不能替代实际审查。

## 必须拆开的覆盖数据
游戏报告至少拆分：代码存在、单元行为已验证、模式可启动、正常流程可通关、资产动画覆盖、不同种子的成功与失败、目标设备实测。

不要实际只测了 50 关都能启动，却写成“50 关全过”。自动玩家没用过的武器或单位，可以通过独立的机制测试，但整关平衡仍属未验证。至少用不同策略覆盖关键战术单位，不让一个最强阵容掩盖其他单位无效的问题。

普通输入允许用自动键鼠或手柄模拟，但不允许直接加血、清敌、改胜利条件或跳过波次。不具备完整通关能力时，如实记录阻断及缺陷来源，不得为了证明可通关而偷偷降低正常难度。

## 明确的失败例子
- 隐形墙、逻辑软锁、环境判定错误、碰撞导致正常路线走不通。
- 攻击状态、命中时刻、挂点、方向、脚点明显不一致；新美术违反 Base 的场景几何或图层规则却被“调像素”掩盖。
- 核心敌人或 Boss 没有有效动作；重要 UI 被遮挡；正式版本静默使用未被接受的占位资源。
- 损坏的存档破坏进度、不同游戏之间串档、刷新后无法继续。
- 发行包中的测试接口可以修改状态；存在未知的联网依赖；研究原件被打进包里。
- 修改测试数据、禁用校验，或只挑成功的种子来宣称全面通过。

“脚点误差不超过 2px”“60fps”之类的具体数字，由项目的世界比例和目标设备决定，Skill 层面不固定。

## QA 的独立性
可选值：self_review、separate_context_same_environment、independent_reviewer、external_approval（仅用于发布批准）。按实际情况记录：同一个 Agent 切换角色仍是 self_review；换一个软件不自动等于独立；独立 Agent 的审查也不等于法律保证。

review 模式默认不修改受审代码，失败项写回任务池。auto 模式下，同一个执行者可以先审查，再切回实施修复，最后重新测试。缺少真人审查不应让其他工作停下，但最终标记必须准确。

## 自动检查要包含失败案例
校验器必须用已知错误的数据做反例，例如缺帧、错误的资源 ID、错误的锚点、损坏的存档、不合法的部署配置，不能只测完美输入。资源替换不应改变规则时，可以比较同一输入、同一种子下不含渲染细节的模拟状态摘要。

## 发行状态不混淆
项目推进状态与发布批准分开记录。可以同时处于“工程候选已打包”和“视觉/法务/真机待确认”的状态，但不能标题写“商业版已完成”，正文却说核心门禁都没通过。
