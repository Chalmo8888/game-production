# 游戏策划规范（G1）

目的：在大量内容开发和美术生产之前，确定“这款游戏是什么、为什么好玩、怎样验证”，并把它变成开发可以直接执行的配置和任务。只列几个概念名称不算策划。

## 输入
- 用户的主题、目标、平台、规模和授权边界（写在 GAME.json `brief` 和 GAME_DESIGN 第 0 节）。
- 绑定 Base 的 START_HERE、BASE_HANDOFF 和创作者工具包：核心能力、扩展点、资产契约、已知限制（见 [HANDOFF_CONTRACT](HANDOFF_CONTRACT.md)）。
- 逆向研究记录（`.production/bases/<id>/re/` 中的能力等价矩阵和表现研究）：哪些机制已验证、哪些只是推断。只读取，不修改。
- 之前游戏的 retrospective：可复用能力和教训，但不复制它们的内容。

## 各节要求（模板第 1–17 节，标题不可删除）
1. **名称与定位**：一句话卖点、与研究对象和同 Base 其他游戏的区别。
2. **目标用户**：玩家画像、平台习惯、单局时长预期。
3. **类型与核心体验**：玩家每分钟在做什么决策，情绪曲线是什么。
4. **世界观与主题**：要能支撑单位、关卡和美术方向；剧情只在适用时写。
5. **核心玩法循环**：分钟级、关卡级、长期三层，每层写输入、反馈和奖励。
6. **继承与改良**：表格逐项写明研究对象中的机制是继承、改良、替换还是删除，以及理由和来源边界。
7. **操作与交互**：输入方式、手势/键位、误操作保护、可达性。
8. **玩法主体**：单位/角色/敌人逐个写定位、战术作用、关键数值、行为规格，以及与其他主体的差异。不能只是换皮。
9. **技能、道具、装备**：效果、数值、获取方式、相互作用；不适用时说明原因。
10. **经济与成长**：资源来源和消耗、成长曲线、防止数值膨胀的手段。
11. **关卡与难度曲线**：逐关写目标、新元素、敌人与布局、时长、难度位置和预期的失败原因。关卡很多时可以另建 `design/LEVEL_PLAN.md`，在这里放链接和摘要。
12. **Boss 与特殊事件**：阶段、招式、破解方式；不适用时说明原因。
13. **UI 交互**：主菜单 → 选择 → 局内 HUD → 结算 → 存档，每个界面的信息和操作。
14. **内容规模与制作顺序**：最小完整版本是什么，扩展批次怎么排，依赖关系如何。
15. **验收标准**：可以执行的条目，写明操作、期望结果和对应门禁（Q01–Q08）。
16. **Base 依赖与扩展划分**：哪些来自共享 Base，哪些是本游戏的扩展（放在游戏目录），哪些需要反哺 Base（需要兼容性和回归）。
17. **配置需求、行为规格与开发任务**：任务 ID、产物路径、依赖、验收方法，同步写入游戏 BACKLOG。

## 质量要求
- 数值有单位和初值，标明哪些是待平衡的候选值。
- 每个玩法主体至少有一个“只有它能解决”的场景，否则就是重复内容。
- 难度曲线说明新元素的引入节奏，不能只写“逐渐变难”。
- 不需要的系统写“不适用 + 原因”，不要为了填满模板而硬加剧情、装备或 Boss。
- 与 Base 能力冲突的设计，要么改设计，要么在第 16 节提出反哺方案，不得默默假设引擎支持。

## 出口（D01）
- 模板标记 `TEMPLATE_UNFILLED` 已删除，第 1–17 节齐全（工具会检查）。
- 第 17 节的任务已经进入 BACKLOG，验收标准可以映射到门禁。
- D01 记录检查者和证据（例如策划自审清单或审查记录），并标明真实的独立性。
