# 复用优先、来源可追溯、必要时独立实现

这些是工程风险控制规则，不是法律意见，也不是“可商用证明”。疑难的权利问题交给权利人或有资质的专业人士确认；AI 做一次审计不等于获得最终授权。

## 两层来源记录
- **Base 层**（`.production/bases/<id>/RIGHTS_LEDGER.md`，门禁 B02）：引擎和 Core 代码、工具、测试、依赖、共享数据和共享资产。B02 PASS 是 COMMERCIAL_BASE_CANDIDATE 的前提。
- **游戏层**（`games/<id>/.production/RIGHTS_LEDGER.md`、`ASSETS.json`，门禁 Q08 → R03）：本游戏的美术、音频、字体、文本、关卡数据和品牌名称。
- 每款游戏的公开发布都需要两层记录齐全，并且有 R04 外部批准。Game 01 的权利结论不能直接套用到 Game 02。

## 先保留成果，再判断边界
研究、可运行的参考、测试思路、独立工具、资产接口和来源清单都可能有价值，新的实施者不得自动丢弃。对每个模块分别选择：KEEP（有依据保留）、ADAPT（允许适配）、REPLACE（需要独立替换）、QUARANTINE（只在隔离环境中研究）、REVIEW（证据不足）。

目录归属、最后保存文件的人、代码行数、有没有反编译地址注释，都不能单独作为法律结论。要检查许可证、作者、上游关系、依赖、可执行发行物和资源来源。不要断言“GitHub 上公开 = 可以自由商用”，也不要认为“用了开源代码 = 必须全部重写”。

## 逐项资产记录
代码、脚本、测试、结构化数据、关卡设计、资源映射、图像、音频、字体和品牌名称分别记录依据与用途。AI 自己写的工具也可能直接搬用了原实现，需要检查。运行时可以替换图片，不等于游戏代码已经清权。

## 高风险代码的处理
没有足够使用依据的反编译代码或专有实现，不进入 Base 和发行工程，不做逐行翻译、改名或 AI 改写来规避来源。可以保留有权开展的研究成果，提炼成通用规则、原创设计和经过筛查的行为需求，再独立实现。项目要求严格的洁净室时，需要真实的访问隔离、独立的实施者和过程记录；仅仅新开一个会话或文件夹，不足以自称洁净室。

同一个 Agent 可以完成一般工程的全流程，前提是项目的来源隔离要求允许；不能借“工具无关”绕过专门设置的隔离边界。研究材料的本地路径不得通过 HANDOFF 让受限的实施者重新读到。

## 不默认强制精确复刻
记录用户真正要保留的玩法能力和差异，而不是逐字照搬原作的全部 UI、角色、数值和关卡。有充分授权的原版或自有源码，可以在许可边界内改良；授权不明时，按通用机制和原创数据独立实现，并保留需要确认的事项。基于同一个 Base 的不同游戏，应当在定位、内容和美术上真正有所不同（G1 第 1、6、8 节）。

## 打包与同步
发布包要排除研究原件、凭据和未获准的材料；但不得为了“包里没有源码”而删除许可证要求提供的源码、声明或相应文件。私有仓库也不意味着可以任意上传第三方材料，仍需审查授权。跨设备同步前，区分可共享的规格和受限的研究资料。

只要还有可执行的任务，权利待确认就不会阻止全部开发；它只阻止相关的复用和公开发布。如果项目唯一可行的路线取决于授权，就记录真实阻断，而不是悄悄开始庞大的重写。
