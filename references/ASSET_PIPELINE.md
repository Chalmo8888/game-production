# 资产生产、替换与集成契约（不绑定生成工具）

## 两层资产接口
- **Base 资产接口**（`.production/bases/<id>/CAPABILITIES.md` 第 4 节，B05）：引擎支持的格式、ID 规则、动画方式、锚点约定、导入与校验命令。所有游戏共用这一层。
- **游戏资产计划**（`games/<id>/design/ART_ASSET_PLAN.md`、`ANIMATION_SPEC.md`、`.production/ASSETS.json`）：本游戏具体有哪些资产、什么风格、目前是什么状态。不得要求 Base 不支持的格式；确实需要时，走 Base 的反哺和版本流程。

## 先保留现有管线
检查已有的加载器、图集、骨骼或逐帧动画、字体与音频映射。已有工具经过来源审查和功能验证可以使用时，就继续用；不要因为换了 Agent 就重建。恢复了资源加载契约，不代表恢复了作者的原始美术制作工程。

资源路径属于制作层，游戏引用使用稳定的语义 ID。格式由项目决定，不绑定 unit.json、Spine、Phaser、WASM 或某个生图 API。

## 契约字段
每项资产记录：ID、用途、状态、必需动作、朝向、逻辑单位尺寸、输出尺寸范围、缩放、pivot/脚点、发射/命中/挂载点、图层、播放方式、是否循环、表现事件、音频、导入命令、测试场景、来源与预算。契约有版本号，修改时列出受影响的全部使用方。

移动、冷却、伤害和碰撞以显式的逻辑规则为准。图像大小、透明裁切、帧排列不应暗中改变规则。继承来的实现确实存在这类耦合时，建立适配层和兼容测试，不能直接“解耦”却破坏现有手感。

## 生产顺序
1. G2：选一个有代表性的单位或角色，加一个场景，完整走一遍：需求 → 生成或制作 → 加工 → 导入 → 运行时检查 → 逻辑回归。
2. 在 ASSETS.json 中标为 verified 之后，再按同一风格、同一契约批量扩展。不要一口气生成数百张，到最后才发现图集切不出来。
3. G4：分批生产，每批都要走到 integrated → verified。

生成工具由环境能力决定。只使用真实可以调用且在预算授权内的工具，批次可控，失败重试有上限。没有生图工具时，先完成契约、加工器和其他任务再交接；不随便抓取商业游戏的资源，不把程序生成的占位图称为正式手绘资产。

可以使用逐帧、骨骼、纸娃娃或合理的程序动画，不要为了“必须逐帧”而否定有效方案。验收看实际的动作、脚点、挂点、连贯性和战斗同步，不看文件数量。

## 状态（ASSETS.json）
`planned` → `source_generated` → `processed` → `integrated` → `verified`，或者 `rejected`。
- source_generated 之后必须填写 provenance（工具、作者或来源）。
- integrated/verified 必须有 license（使用依据）和 runtime_files（游戏实际加载的文件，带 SHA-256）。
- verified 必须有证据（连续序列、实机截图或录像、检查日志）。
- rejected 必须写 rejected_reason。
- `scope: base` 表示由 Base 提供的共享资产，路径相对于 Base 的 code_path；其他资产的路径都相对于游戏目录，不能引用其他游戏的文件。

## 运行时验证
- 源图只是生产原料；runtime atlas/clip、注册表和实机序列才是集成证据。
- 检查透明边界、缩放、朝向、攻击瞬间的发射位置、受击和死亡、场景碰撞与图层。
- UI 要在不同窗口尺寸下检查；字幕不能持续遮挡战斗；像素字体和中文的覆盖范围要明确。
- 正式资源清单要扫描实际的包。开发模式下缺失时显式提示回退；候选包中的必需资产不能默默回退到占位。
- 声音要验证播放、音量总线、并发、循环与结束、用户手势后的恢复。文件存在不等于已经试听通过。
- 替换前后运行相关的机制回归；单纯的美术改动不应改变伤害、移动或冷却。

## 交接
契约、已接受的资产、被拒原因、剩余清单、工具调用记录和输出规范一起交接；接手者不需要知道前任用的是什么软件。未完成的音乐和字体要记录下来，不能默认它们不需要。
